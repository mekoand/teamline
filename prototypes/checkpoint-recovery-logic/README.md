# PROTOTYPE — 检查点与恢复状态模型

运行：

```bash
bun run prototypes/checkpoint-recovery-logic/cli.ts
```

## 要回答的问题

当 Teamline 区分阶段检查点、暂停保存点与崩溃后的待处理现场，并要求旧执行完成围栏后才能签发新租约时，这套状态模型能否同时避免双写、保留意外中断后的现场，并给用户提供清楚的安全恢复与现场接续选择？

这个原型只在内存中模拟状态，不接真实 Codex、Git 或数据库。Bun 只是临时运行载体，不构成个人内核 v0 的技术栈决定。

`0` 只会重新初始化演示夹具，方便从头尝试下一条路径；它不是产品动作，也不属于被验证的状态机。真实委托不能用“重置”绕过围栏或现场保存。

建议依次尝试：

1. `s → w → b → v → w → x → r`：未围栏时安全恢复应被拒绝；
2. 接着 `o → f → r → a → r`：围栏后仍不能直接重置；独立保存现场后，才能回到阶段检查点；
3. `0 → s → w → b → w → v`：验证期间工作树变化时，阶段检查点应被拒绝；
4. `0 → s → w → p → u`：主动暂停应从暂停保存点继续，但不能增加已完成阶段；
5. `0 → s → w → i → r → a → r`：暂停保存失败后，必须先独立保存现场，再退回起始基线；
6. `0 → s → w → x → f → c → a → c`：现场接续也必须先保存独立引用，并标记为非保证恢复；
7. `0 → s → w → x → f → d → r → a → r`：现场保存失败时禁止恢复，重试成功后才能恢复。

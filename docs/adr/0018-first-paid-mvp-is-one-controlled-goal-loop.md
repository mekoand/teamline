# The First Paid MVP Proves One Managed Goal Loop

The paid team MVP reuses the local execution kernel already validated through a single-repository, single-tool personal loop. An owner creates a work goal from repository and external requirement references. The control layer generates a plan and resolves an effective rule set. After the owner confirms and authorizes it, the local execution host starts the existing AI coding tool. The console records run state and checkpoints, and supports pausing, recovery, and handoff. After the tool exits, Teamline runs the required validation commands confirmed in the plan and saves the final diff and command results. Passing work enters review; failed work remains marked as needing attention. The paid team MVP does not add separate AI acceptance, AI risk reports, or repeated stage summaries. The overview and execution map are two views of the same loop, while quota, budget, and tool availability participate as resource constraints.

The paid pilot integrates one code hosting platform, one general local command entry, and the deep Codex integration validated by the personal kernel. The exact integration surface is chosen by a capability review rather than by each pilot team. It excludes automatic cross-tool switching, general documentation, chat, bidirectional synchronization, free-form canvases, hosted agents, and arbitrary natural-language rule verification.

## 中文

# 首个付费 MVP 只证明一条受控目标闭环

团队付费 MVP 复用已经在单仓库、单工具个人闭环中验证的本地执行内核。负责人从仓库和外部需求引用创建工作目标，控制层生成计划并解析生效规则集；负责人确认并授权后，本地执行端启动现有 AI 编码工具。控制台持续记录运行状态与检查点，支持暂停、恢复和交接。执行工具结束后，Teamline 运行计划中预先确认的必需验证命令并保存最终差异与命令结果；通过后进入待验收，失败则继续标记为需要处理。团队付费 MVP 不增加独立 AI 验收、AI 风险报告或重复的阶段汇总。运行总览和执行图只是这条闭环的不同视图，额度、预算和工具可用性作为资源约束参与执行决策。

付费试点只接入一个代码托管平台、通用本地命令入口，以及个人内核已经验证的 Codex 深度接入；具体接入面由能力闸门决定，不再由试点团队临时选择工具。它不包含自动跨工具切换、通用文档、聊天、双向同步、自由画布、托管 Agent 或任意自然语言规则验证。
